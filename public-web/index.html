Stouter is a lightweight service mesh for distributed clusters. It discovers services through gossip, routes traffic over mutually authenticated tunnels, and reaches nodes hidden behind NAT — all from a single binary and one JSON file.

What is Stouter?

A small mesh that solves the three hard parts.

No central registry, no sidecar fleet, no control plane to babysit. Each machine runs one stouter process, and together they form a self-organizing cluster.

Service discovery

Nodes advertise their services and learn about peers through a gossip protocol. The service catalog is versioned and replicated across the cluster automatically.

Secure routing

Every inter-node connection is encrypted and mutually authenticated with a per-cluster certificate authority. Stouter generates the PKI for you on first start.

NAT traversal

Nodes that can't accept inbound traffic keep a pool of outbound “reverse” connections to relays, so requests still find their way home through firewalls.

How it works

From a local port to a remote service, in four steps.

  1. Nodes gossip

    Every ten seconds each node syncs with its peers, exchanging the service catalog and the list of known nodes. The highest config version wins, so a change made anywhere spreads everywhere.

  2. Subscribers expose local ports

    A node in subscribe mode opens a local TCP proxy for each service it's allowed to see, and publishes the port mapping on a small REST API.

  3. A healthy node is chosen

    When your app connects, Stouter picks a node hosting that service with health-aware round-robin, reusing a multiplexed session, a reverse connection, or a pre-warmed tunnel when it can.

  4. Bytes flow, securely

    The request travels over a mutually authenticated TLS tunnel with replay protection, and data is proxied in both directions until the connection closes.

Three modes, one binary

node
Hosts services and relays tunnels for other nodes.
subscribe
Discovers services in the cluster and exposes them as local TCP proxies.
nodeSubscribe
Does both: hosts services locally and proxies remote ones.

Quick start

Bring up a two-node cluster: one node that hosts a service, and one that consumes it.

1. Configure the first node

Create /etc/stouter/stouter.json on host1:

{
  "mode": "node",
  "bind": "0.0.0.0:8080",
  "advertiseAddr": "10.0.0.1:8080",
  "nodeId": "host1",
  "knownNodes": [],
  "tlsDir": "/etc/stouter/tls",
  "dynamicConfig": { "version": 1, "serviceGroups": [] }
}

2. Register a service and start the node

Add a service running on local port 3000 to the config, then start the daemon:

stouter --config /etc/stouter/stouter.json service add --group web --name api --port 3000
stouter --config /etc/stouter/stouter.json

On first start Stouter creates a cluster CA in tlsDir.

3. Issue a certificate for the second node

On host1 (the CA node), then copy the output to host2:

stouter --config /etc/stouter/stouter.json cert issue --node host2 --out ./host2-tls
scp ./host2-tls/* host2:/etc/stouter/tls/

4. Start a subscriber

On host2, point knownNodes at host1 and use subscribe mode:

{
  "mode": "subscribe",
  "bind": "0.0.0.0:8080",
  "nodeId": "host2",
  "knownNodes": ["10.0.0.1:8080"],
  "tlsDir": "/etc/stouter/tls",
  "dynamicConfig": { "version": 0, "serviceGroups": [] }
}

Once gossip syncs, ask the local API which port to use for api:

curl http://127.0.0.1:5381/services/api

Configuration

Each instance is configured by a single JSON file, passed with --config (default stouter.json). Validate it at any time with stouter check.

FieldDescription
modenode, subscribe, or nodeSubscribe.
bindAddress to listen on, e.g. 0.0.0.0:8080.
advertiseAddrAddress peers use to reach this node. Defaults to bind.
nodeIdUnique identifier for this node, typically its hostname.
knownNodesBootstrap peer addresses (host:port) for initial gossip.
tlsDirDirectory for ca.crt, ca.key, node.crt, node.key. Required.
outboundOnlySet true for nodes behind NAT. Disables the listener and uses reverse connections.
reversePoolSizeIdle reverse connections kept per relay peer. Default 64.
subscribeFilterLimits which groups or services a subscriber proxies.
adminCnsCertificate common names allowed to make remote admin changes. Empty disables admin RPC.
apiPortLocal REST API port on 127.0.0.1. Default 5381.
dynamicConfigThe versioned, gossip-replicated service catalog.

Registering services

Services are organized into named groups. Each entry maps a service name to a port on the node that hosts it, with optional domains. You can edit the catalog directly:

"dynamicConfig": {
  "version": 1,
  "serviceGroups": [
    {
      "name": "web",
      "services": [
        {
          "name": "api",
          "nodeId": "host1",
          "nodePort": 3000,
          "domains": ["api.example.com"]
        }
      ]
    }
  ]
}

…or manage it from the CLI. Without --remote, commands edit the local config file; with --remote, they change a running cluster and the update spreads by gossip:

stouter service add    --group web --name api --port 3000
stouter service rename --group web --from api --to api-v2
stouter service remove --group web --name api-v2
stouter service list   --remote 10.0.0.1:8080

Subscribers can choose which services to proxy. A service is included if its group or its name is listed; with no filter, everything is proxied.

"subscribeFilter": { "serviceGroups": ["web"], "services": [] }

Certificates

All traffic between nodes uses mutual TLS against a single cluster CA. Stouter loads certificates from tlsDir in this order:

  1. ca.crt + ca.key — load the CA and mint a fresh node certificate in memory.
  2. ca.crt + node.crt + node.key — use a pre-issued node certificate.
  3. Nothing present — generate a new CA (written to disk) and node certificate (kept in memory).

To add a node to an existing cluster, issue its certificate from the CA node and copy the files into the new node's tlsDir before starting it:

stouter cert issue --node host3 --out /path/to/host3-tls

Nodes behind NAT

If a node can't accept inbound connections, set "outboundOnly": true. It will dial out to every reachable relay peer and keep reversePoolSize idle connections registered with each. Relays use those connections to forward requests back in, and the pool is replenished immediately after each use.

CLI reference

CommandPurpose
stouterRun the daemon using the config's mode.
stouter initSet nodeId to this host's name, save the config, and announce to known peers.
stouter checkValidate the configuration file.
stouter status [--remote addr]Show the status of a running daemon.
stouter service addRegister a service (--group, --name, --port, --domains, --node).
stouter service listList services in the cluster.
stouter service renameRename a service within a group.
stouter service removeRemove a service from a node.
stouter service moveMove a service between clusters (--from, --to).
stouter cert issueIssue a node certificate signed by the cluster CA.

Global flags: -c, --config <path> and --cert-dir <dir> (client identity for --remote calls). Remote mutations require the client certificate's CN to be listed in the target's adminCns. Set RUST_LOG to control log verbosity.

Local REST API

Subscribe-mode nodes serve a small API on 127.0.0.1:5381 (change it with apiPort), so local processes can find services without static port configuration.

EndpointReturns
GET /servicesAll proxied services and their local ports.
GET /services/{name}The local port for one service.
GET /metricsPrometheus metrics.
GET /__healthHealth check.

Running in Docker

Use host networking so the proxies and listener bind directly on the host, and mount your config directory:

docker run -d --name stouter --network host \
  -v /srv/stouter/config/:/srv/stouter/config/ \
  stouter --config /srv/stouter/config/stouter.json
